## v0.6.11 待核对请求恢复修复（2026-10-19）

### RCA 结论

- 状态：插件缺陷已复现并修复；线上异常的整体原因部分确认。
- 现象：线上插件为 v0.6.10，存在已结束但持续待核对的请求；部分请求在 CPA Manager 中能查到 Token。
- 直接原因：`Generate=false` 用量被直接忽略，但此前已经创建的准入仍停留在 pending，随后超时转为 review。另有同一 TraceID 的迟到用量归错请求、相同执行的补全通知被去重丢弃的可复现路径。
- 根因：准入阶段未采用宿主的非生成标志；关联逻辑假设同一 TraceID 只需选择最新请求；去重没有区分完整记录与尚待补全记录。
- 系统性根因：准入、完成、用量三个入口未一致维护非生成请求的状态；原回归没有覆盖同一连接多次执行、用量通知乱序及不完整通知升级。请求状态还会被最后一条通知覆盖，隐藏同一请求其他未完成计量的执行。
- 关键因果链：非生成请求被准入 → 非生成用量直接返回 → 准入无结算路径 → 超时待核对。其他分支为：同一 trace 多次准入 → 较早执行用量迟到 → 归入最新准入；空用量先入账 → 完整通知 ID 已存在 → 补全被忽略。

### 证据

| 判断 | 类型 | 证据与来源 |
| --- | --- | --- |
| 非生成请求留下待核对 | 事实 | 只读对比插件备份与 CPA Manager 监控：一条 Responses WebSocket 请求有 19,126 Token、`generate=false`，插件对应准入为 review、无 usage；同一 trace 后续 8 次实际生成均有正常记录 |
| 截图中的两条 Claude 请求没有可回填的 Token | 事实 | 按插件准入 trace 查询监控，两条均为 Devin 流式生成，监控 Token 分项和总量均为 0；插件各有一条 0 Token、不完整记录，完成结果均为 canceled |
| 去重与关联缺陷可重复触发 | 事实 | 修复前六个新增用例全部失败：非生成准入、非生成通知关闭、共享 trace 迟到通知、重叠候选拒绝、空通知补全、重试完整性；修复后通过 |
| 手工核对不会被空通知覆盖 | 事实 | 补充回归验证：人工记录保留；随后完整真实用量替换人工记录，重复通知只保留一笔账 |

### 已排除解释

- 本次抽查的待核对没有非零 Token 的未计价用量，不能用缺少模型价格解释截图中的全零记录。
- 截图中的两条通知已经关联到正确准入，因此它们不属于模型别名或请求 ID 匹配失败；监控中存在记录，但该记录的 Token 本身也是 0。
- `generate=false` 请求在监控中有输入 Token，不等于插件应按实际生成收费；原用量入口明确忽略此类请求，本次修复保持该既有行为并补齐准入／完成状态。

### 异常状态溯源

- 适用约束：宿主明确声明非生成请求时，插件只检查权限，不留下等待生成用量的准入；对已准入实际生成，仅完整、可归属的真实用量可结束核对，重复执行通知不得增加扣费。
- 依据：宿主 `Generate`／`Metadata.generate` 契约、原非生成旁路行为、项目缺失用量核对及重复通知去重契约。线上非生成样本命中；本地用例复现状态违反。
- 状态路径：宿主携带非生成标记 → 准入入口忽略标记并写入 pending → 用量入口丢弃通知 → 完成后 30 秒转为 review。
- 调查边界：未取得两条取消 Claude 请求的原始上游流；无法确定取消前是否存在尚未发布的最终 Token，也不能从相邻请求、模型平均值或请求是否成功推算。

### 修复与防复发

- 准入识别 `Metadata.generate=false`，保留权限校验；完成及用量入口在不存在账本时结束对应的旧非生成准入。
- 请求 ID 优先；TraceID 回退用执行开始时间和准入起止时间匹配，只接受唯一候选，避免把迟到通知计入新请求。
- 相同执行的不完整记录允许被完整记录原位替换，并写入 `repair_usage` 审计；已完整记录不被重复或空通知覆盖。
- 由全部执行共同计算请求是否仍需核对；真实重试分别记账，空通知不覆盖人工结算。
- 验证：修复阶段 `cargo test --locked`、更新为 v0.6.11 后 `cargo test --offline` 均为 59 项通过；4 项凭据桥接测试、`cargo fmt --check`、`node --check ui/app.js`、注册表与差异检查通过。`scripts/build.ps1 -ReleaseAssets` 完成 Windows x64 Release 包构建。8 个新增回归位于原有 Rust 测试模块，没有新增测试文件；测试配置写入 `temp/` 并清理。

## v0.6.6 对齐 CPA-Manager-Plus 默认服务等级计价（2026-10-13）

### RCA 结论

- 状态：部分确认。默认等级错误加价的代码路径和费用影响已确认；历史首笔用量未纳入插件汇总的具体原因尚未取得账本证据。
- 现象：同一密钥、同一 Devin Claude 模型，Manager 展示 17 次调用、`2.74 USD`，插件展示 17 条、`4.386511 USD`，没有待核对或未计价记录。
- 直接原因：17 次监控事件均为 `service_tier=auto`；插件将其归为未知，再在标准和 priority 规则间取最大费用。该模型在插件中的 priority 输入、输出、缓存读取、缓存写入费率恰好都是标准价的两倍。
- 根因：`Price::cost()` 将“没有确认使用付费等级”当作“应按最贵等级计费”。这与用户要求参考的 CPA-Manager-Plus 默认计费口径不同；价格同步成功不会纠正等级选择。
- 系统性根因：已有价格测试明确断言未知等级取最高价，Devin 引擎用例只使用不含 priority 的平价表，没有覆盖真实自动价格包含服务等级规则时与参考系统的费用一致性。
- 关键因果链：宿主 auto → `service_tier()` 返回 `None` → `Price::cost()` 遍历各服务等级取最大费用 → priority 双倍价格写入账本 → 金额额度偏高。

### 证据

| 判断 | 类型 | 可复核证据 |
| --- | --- | --- |
| 两套基础费率相同 | 事实 | 只读查看 Manager 价格页与插件 `/state`：输入 4、输出 20、缓存读取 0.2、缓存写入 5 USD/百万 Token；Manager 该条来自 OpenRouter、没有服务等级规则，插件来自 models.dev、另有 8/40/0.4/10 的 priority 规则 |
| Manager 17 笔费用正确对应标准价 | 事实 | 浏览器只读捕获已筛选 `/monitoring/analytics`：输入总量 3,202,400、输出 11,032、缓存读取 2,811,926、缓存写入 390,428；普通输入 46，费用为 `(46×4 + 11032×20 + 2811926×0.2 + 390428×5) / 1000000 = 2.7353492` |
| 后 16 笔按 priority 可重现插件现值 | 事实 | 按监控逐笔用量套用插件 priority 费率并逐笔向上取六位小数，合计恰为 `4.386511`，Token 为 `3,105,477`，均与插件 `/state` 一致 |
| 第一笔尚未纳入插件 Token 汇总 | 推断 | Manager 全部 17 笔归一化总量为 3,213,432，与插件差 107,955，恰好是 10:15:10 首笔总量；首笔标准费用为 `0.542096`。不能由汇总反推其具体人工结算或历史处理过程 |
| 参考系统不将 auto 当 priority | 事实 | 对照 CPA-Manager-Plus 提交 `9d719fc8cca362f7b56d294a2ad056ae99cfeba6` 的 `apps/web/src/utils/usage.ts`（`calculateCost`）及 `apps/manager-server/internal/service/pricing/cost.go`（`CostForModelWithServiceTier`）：仅匹配指定等级规则，auto 不触发 priority 加价 |

### 已排除解释

- 不是两边基础单价不同：四项基础费率一致。
- 不是仅由两位／六位小数显示差异造成：17 笔逐笔向上取六位小数为 `2.735354`，仅比 Manager 浮点汇总多 `0.0000048 USD`。
- “今天”与“每周”并非本次差额的充分解释：虽然时间窗口不同，但插件当前金额和 Token 能同时由今天后 16 笔的 priority 重算精确复现；历史首笔仍须单独核验。

### 异常状态溯源

- 适用约束：在按 CPA-Manager-Plus 默认口径计费、且实际等级为空或 auto 时，不得仅因为目录中存在 priority 规则就使用 priority 价格。
- 约束依据：用户要求对齐参考系统，及上述固定提交的前后端计费实现。本次 17 笔事件均为 auto，前提命中。
- 首次违背位置：等级归一化为 `None` 后，原 `Price::cost()` 的遍历与 `sum.max(cost)` 选择了未被事件确认的付费档。
- 调查边界：未读取插件完整历史账本，未假定首笔被人工归零；未修改线上设置、价格、权限或用量。

## v0.6.5 Devin 用量口径与待核对不拦截（2026-10-13）

- 现象：`devin/claude-opus-5-5` 已同步价格，请求成功后 Claude 渠道显示 0 USD、“1 条未计价”和“处理待核对（1）”，后续请求返回 503 `usage_needs_review`。
- 根因：CLIProxyAPI v8.0.4～v8.0.27 的 `DevinExecutor` 以 `Provider=devin`、`ExecutorType=DevinExecutor` 上报用量，`InputTokens` 含缓存读取、不含缓存写入，`TotalTokens` 也不含缓存写入。插件口径表未覆盖该执行器，用量被判为 Token 不完整，只记 Token 不计价并转待核对。v0.6.1 的回归用例假设执行器为 `claude`、输入为 4，与宿主实际记录不符，故未拦住该问题。
- 在 v0.6.4 原代码上用宿主字段结构和截图数值构造样本（输入 4、输出 155、缓存写入 107,800、总量 159）复现：`complete=false`、输入被截为 0、总量 159。修复后归一为普通输入 4、计价总量 107,959；使用仅含基础费率 4/20/0.2/5 USD 每百万 Token 的测试价格，结算 `0.542116 USD`，状态为已结算。缓存写入数取自截图的四舍五入展示，不是线上原始记录；该费用也不代表含 priority 规则、服务等级为 auto 时的计价结果。
