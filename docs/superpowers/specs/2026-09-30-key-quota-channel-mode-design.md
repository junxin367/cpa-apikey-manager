# 密钥总额度开关与渠道／模型配置方式

日期：2026-09-30。

状态：已按用户“直接开发”指示实现 v0.3.0。核心交互和渠道含义已在对话中确认，用户选择直接实施；本文保留实现依据，实际验收范围见 `docs/verification.md`。

## 1. 目标与已确认理解

管理员需要按使用范围管理一把密钥，而不必对同一系列的每个模型重复配置。

已确认的核心方案：

- “密钥总额度”增加独立启用开关；关闭时保留单位、上限和已用量，继续记录消耗。
- 每把密钥在“按渠道”和“按模型”之间二选一。一个选择同时决定权限和额度的配置维度。
- 按渠道时，GPT、Claude 等系列各自作为一个渠道，渠道内模型共享该渠道额度。
- 按模型时，模型分别设置权限和额度。
- 两套规则保留，只有选中的一套参与权限和额度判断。
- 密钥总额度独立于上述选择，可与当前生效方式的额度共同限制请求。
- 渠道按模型系列划分，不按上游连接划分。同一 GPT 模型通过不同上游调用，仍计入 GPT 渠道。

现有基础是 v0.2.0 的总额度与单模型额度实现。前端目前只用模型名称识别 GPT、Claude 等筛选分组，后台尚无渠道规则；总额度通过有无 `total_quota` 表示是否限制。

成功标准：界面清楚区分启用状态与额度数值；同一请求只记录一次；关闭／开启总额度或切换配置方式都不清空本周期用量；旧配置升级后保持原先权限和额度行为。

## 2. 方案比较与选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A：固定渠道、记录请求归属，推荐 | 后端统一识别模型系列，在准入和用量记录中保存渠道，按总量／渠道／模型汇总同一账本 | 符合当前已知渠道；归属稳定，便于核对；新增系列需要更新识别规则 |
| B：管理员维护模型分组 | 提供分组与成员管理，查询时按分组成员汇总模型用量 | 支持任意自定义渠道；需额外成员管理界面，并解决调整成员后历史费用重新归属的问题 |

本设计采用 A。渠道名称来自已确认的模型系列，不增加自定义渠道或渠道成员编辑功能。设计中的“其他”承接暂不能识别的实际模型。

## 3. 用户界面

密钥详情按以下顺序组织：

1. 密钥备注、额度周期和顶部保存操作。
2. 密钥总额度区域，标题旁显示“启用总额度”开关。
3. “配置方式”互斥选项：按渠道／按模型。
4. 当前方式的权限与额度表格。

### 3.1 总额度开关

- 已启用：展示上限、已用、剩余、重置时间，以及待结算／待核对状态。
- 已关闭且有保存的额度：显示“总额度已关闭”和保留的配置摘要，隐藏进度和剩余额度，避免呈现为仍受总上限限制。
- 从未配置：默认关闭，显示“尚未配置总额度”。
- 总额度关闭后仍可查看本周期已记录用量；金额存在未计价记录时显示“待计价”，不能视为零费用。
- 关闭只停止总额度检查。当前方式下的权限和额度仍然生效；存储故障保护也不取消。
- 总额度为 0 且启用时阻止新的生成请求；0 与关闭是不同状态。

开关提交方式：

- 有已保存额度时，切换开关先进入密钥草稿，通过顶部“保存配置”提交；未保存时明确显示草稿状态。
- 首次开启且没有额度时，直接打开总额度编辑弹窗，要求选择 Token／USD 并填写上限；“保存并启用”一次提交，取消则保持原先关闭状态。
- 已关闭时点击“编辑总额度”，允许修改保留值，保存后仍关闭；不会因编辑数值自动开启。
- 总额度弹窗只提供 Token／USD 两种类型，启停统一交给开关，不再同时提供“不限额”入口。渠道／模型额度弹窗继续保留“不限额”选项。
- 额度弹窗如会同时提交密钥草稿，需明确列出其他变更，尤其是配置方式与总额度启用状态。
- 保存失败时不更新“已生效”状态，保留草稿供修正，并说明原因。

### 3.2 配置方式

每把密钥只有一个 `rule_mode`：`channel` 或 `model`。

- 选择方式仅改变草稿，保存后才影响新请求。
- 切换时展示说明：“保存后将按渠道规则判断；已保存的模型规则暂不生效。”反向切换同理。
- 首次切到空规则方式时额外说明：“当前尚未配置渠道规则，保存后未配置渠道将放行；已启用的密钥总额度仍生效。”
- 不把模型额度相加生成渠道额度，也不猜测如何合并互相不同的模型权限。
- 切回原方式时恢复该方式之前保存的配置；用量从同一账本重新汇总。
- 两种方式使用同一把密钥的日／周／月周期和服务器时区。

### 3.3 按渠道

固定展示 GPT、Claude、DeepSeek、GLM、Kimi、其他六行。即使某渠道暂无目录模型，也可以预先设置规则。

表格展示：渠道、已知实际模型数量、权限、渠道上限、本周期已用、操作。模型数量不重复计算别名，也不表示当前上游一定可以调用。

- 权限为未配置／允许／禁止。
- 未配置渠道保持现有放行语义，不单独限额，但仍受已启用的总额度约束。
- 禁止渠道拒绝该渠道全部模型；额度不能覆盖禁止规则。
- 渠道额度为全部实际模型共享的一笔 Token／USD 上限。
- 新发现且能识别到该渠道的模型自动受规则约束，无需重新保存密钥。
- 可展开查看该渠道当前已知模型，便于核对归属；此处不提供单模型权限例外。
- “其他”不是无条件放行区，同样可以设置权限和额度。

### 3.4 按模型

保留现有模型表格和集中编辑弹窗。GPT、Claude 等在此模式下只是筛选项，不是同时生效的渠道规则。

- 已保存的渠道规则全部暂停参与判断，包括禁止规则。
- 未配置模型保持放行、不单独限额的语义；总额度和统一记账仍生效。
- 别名与实际模型共用对应额度，继续保持现有模型权限检查。

示例：总额度为每月 10 USD，GPT 渠道额度为每月 3 USD。GPT 模型费用合计达到 3 USD 时暂停 GPT 渠道；Claude 等其他渠道可继续使用剩余总额度。所有模型累计达到 10 USD 后，总额度阻止该密钥全部新的生成请求。

## 4. 渠道归属

后端是归属的唯一来源。状态接口把渠道信息传给前端，前端不再单独根据字符串猜测权限或额度范围。

识别流程：

1. 生成请求以宿主最终选择的实际模型为准；已知别名先解析到实际目标。
2. 名称只在识别时转为小写；保留原始模型 ID 作为计价、规则和账本标识。
3. 对带 `/` 命名空间的模型，使用最后一个非空名称段识别系列；前面的上游命名空间不决定渠道。
4. 按下表识别，无法明确匹配时进入 `other`。

| 渠道 ID | 显示名 | 名称规则 |
| --- | --- | --- |
| `gpt` | GPT | `gpt`、`chatgpt`、`codex`，或 `o` 后接非零开头整数 |
| `claude` | Claude | `claude` |
| `deepseek` | DeepSeek | `deepseek` |
| `glm` | GLM | `glm` |
| `kimi` | Kimi | `kimi`、`moonshot` |
| `other` | 其他 | 其余名称 |

表中词根必须位于名称段开头，其后为名称结束或 `-`、`_`、`.`、`:` 分隔符；不得仅因任意子串出现词根就归类。例如 `gpt-4o` 属于 GPT，`custom-gpt-copy` 属于其他。

别名注意事项：

- 别名文字包含 GPT，但实际模型为 Claude 时，渠道规则按 Claude 判断。
- 多目标别名在生成请求最终选定实际模型后检查渠道，不能提前仅凭别名文字拒绝或放行。
- 用量回调使用准入记录中的渠道归属，不根据回调里的上游供应商重新分类。
- 纯 Token 计数接口仍只检查权限，不进行额度扣减。已知唯一目标按其渠道检查；已知多个候选时必须全部获准；无已知映射时按请求模型的识别结果检查。计数接口的允许结果不代替后续生成请求的实际模型检查。

新请求保存识别结果。后续版本调整识别规则时，不静默重新分配已记录费用；需要另行设计明确的数据迁移。当前版本不提供手动修改历史归属功能。

## 5. 计量与请求判断

### 5.1 持续记账

为保证总额度关闭期间和不同配置方式之间的用量连续，新版本从启用统一记录起，对所有已识别有效密钥的获准生成请求记账，即使当时没有生效额度。

这会增加相对于旧版“只有限额模型才记账”的记录量，但不增加模型调用。保留请求关联、执行去重、失败请求实际消耗、跨零点归属及迟到用量修正机制。

- 同一执行只有一条用量记录，同时参与总量、对应渠道和模型的汇总。
- 同一模型走不同上游的实际执行分别计入对应调用者的账本；重复回调仍只记一次。
- 总额度关闭不停止记账，不删除或清零累计消耗。
- 准入时有价格则保留快照；没有价格且没有生效金额额度时，记录 Token，金额标记为未计价。
- 回调先按请求 ID／实际模型关联，再按 TraceID／密钥／实际模型关联。仍无法找到准入记录时不写用量，产生不含明文密钥的诊断告警；不能通过读取当前规则反推收费。已有准入而缺失用量的请求继续进入待核对。宿主验收必须覆盖请求 ID 与执行 ID 不同的关联场景。
- 插件停用、安装前或旧版没有记录的请求不能追溯补造。

元数据记录 `continuous_recording_since`，首次启用该行为时写入，重启不修改。每把密钥另存 `recording_since`：迁移时已有密钥取本次统一记录起始时间，之后新增密钥取首次同步时间，移除后重新同步不重置。页面说明：“持续记账启用于此时间，更早仅包含已有记录；插件停用期间无法补算。”本周期起点早于该密钥记录起点时保留提示，不把历史部分汇总称为完整账单，也不承诺已覆盖插件停用的时段。

### 5.2 判断顺序

1. 校验密钥身份、配置来源及存储健康状态。
2. 根据实际模型和该密钥的当前 `rule_mode` 校验权限；另一套规则完全不参与。
3. 对生效额度范围检查待核对、未计价等影响核算的异常。
4. 检查已启用的密钥总额度。
5. 检查当前模式的渠道额度或模型额度。
6. 任一生效金额额度需要当前模型价格时，检查价格是否可用。
7. 记录准入上下文、实际模型、渠道及价格快照，然后放行。

总额度关闭时，不执行总额度耗尽、总金额缺价或总范围待核对拦截；仍检查当前方式的生效额度。

任一生效额度已达到上限时返回 429。启用的 0 金额额度没有历史未计价／待核对阻碍时，即使当前模型没有价格，也应先返回额度耗尽；不能把 0 误认为关闭。

全部额度仍基于已结算用量，已准入的并发或流式请求可能超额，不新增严格预留或硬消费封顶。

### 5.3 重新启用与金额补计

- 重新启用总额度时纳入本周期已记录用量，包括关闭期间的记录。
- 切换配置方式时使用相同账本，不以切换时间为新周期起点。
- 金额额度按每个实际模型自己的价格计算后相加，不设渠道平均价格。
- 仅将生效的金额额度范围纳入补计检查；暂停的规则或关闭的总金额不要求补价，也不妨碍保存其他配置。
- 目标范围存在未计价历史时，必须显示补计金额并由管理员明确确认；缺少相关历史模型价格时无法完成启用。
- 未计价的执行中或待核对请求需先结算／核对；补计与策略保存保持事务一致。
- 总金额与渠道／模型金额覆盖同一条记录时只补计一次。
- 已记录用量高于拟启用额度时允许保存，并明确显示“启用后将立即拦截新请求”。

### 5.4 待核对范围

总额度启用时，任一模型待核对都影响全密钥总量。总额度关闭时，只影响包含该用量的生效渠道额度或模型额度。仅有权限规则而无生效额度时，待核对显示为异常提示，不单凭该记录阻止无额度的新请求。

同一笔异常用量可从总额度、渠道或模型入口处理；所有入口指向同一原始请求，不创建额外结算记录。

## 6. 数据和接口

在现有策略字段基础上新增字段，保留 `rules` 表示模型规则：

```json
{
  "revision": 5,
  "note": "开发团队",
  "period": "month",
  "total_quota_enabled": true,
  "total_quota": { "unit": "money", "limit": "10" },
  "rule_mode": "channel",
  "channel_rules": {
    "gpt": {
      "access": "allow",
      "quota": { "unit": "money", "limit": "3" }
    },
    "other": { "access": "deny", "quota": null }
  },
  "rules": {
    "gpt-4o": {
      "access": "allow",
      "quota": { "unit": "tokens", "limit": "100000" }
    }
  }
}
```

上述示例中，`rules` 保留但不参与当前权限或额度判断；`other` 禁止只作为示例，默认不自动禁止。

约束：

- `total_quota_enabled=true` 必须同时存在有效 `total_quota`。
- `false` 时可以保留有效额度，也可以为 `null`。
- 两套规则都检查字段、单位、数值和渠道 ID 合法性，但只对当前生效的金额范围检查补计条件。
- `rule_mode` 只接受 `channel`／`model`，未知值不能静默降级。
- 沿用策略版本号检查，两个页面并发保存时拒绝过期覆盖。

状态接口：

- 每个模型增加后端提供的 `channel` 和显示名称。
- 保留 `total_usage`、模型 `quotas`，新增按固定渠道 ID 索引的 `channel_usage`。
- 渠道汇总包含 Token、金额、未计价、待结算、待核对及重置时间。
- 返回当前方式和开关状态，使页面能准确区分生效规则与保留配置。

核对接口：

- 现有密钥级／模型级查询继续有效，增加渠道筛选。
- 同时传入模型和渠道筛选时拒绝请求，避免范围含义不明确。
- 人工核对仍按原请求和实际模型执行，沿用其渠道归属。

拒绝响应：

- `quota_exceeded` 的 `scope` 扩展为 `total`／`channel`／`model`。
- 渠道额度错误增加 `channel` 和 `channel_label`，仍包含本次实际 `model`、已用、上限、周期、重置时间、时区及 `Retry-After`。
- 渠道禁止返回 403 `channel_forbidden`，中文说明渠道与实际模型。
- 模型禁止沿用 403 `model_forbidden`。
- 待核对和未计价错误说明影响的是密钥、渠道还是模型，以及对应管理入口。

## 7. 持久化与兼容

请求与用量表增加渠道字段。准入时写请求归属，正常用量和人工核对沿用该归属；不依赖当前策略模式来重建它。

使用版本化迁移补齐历史记录，按历史实际模型进行识别，无法识别的放入 `other`。迁移保持记录 ID、时间、Token、金额、价格快照、密钥标识和人工核对标记不变；不能重算已有费用。

增加按密钥／渠道／时间的用量索引，以及密钥／渠道／状态的请求索引。保留总量和模型查询所需索引。调整初始化脚本，避免每次启动将数据库版本重写回旧值。

旧策略迁移：

| 原状态 | 升级后的状态 |
| --- | --- |
| 缺少 `rule_mode` | `model`，继续使用原模型规则 |
| 缺少 `channel_rules` | 空规则 |
| 缺少启用字段且已有 `total_quota` | 总额度启用，原上限不变 |
| 缺少启用字段且 `total_quota` 为空 | 总额度关闭 |
| 新同步密钥 | 按模型、两套规则为空、总额度关闭 |

管理写接口如果缺少新增字段，沿用该密钥当前已保存的对应值；仅历史数据解码采用上述迁移默认值。这样旧客户端提交不会悄悄切回模型模式、丢掉渠道规则或重新启用已关闭的总额度。完整状态响应始终包含新增字段，新页面显式提交它们。旧客户端若将额度置空但保留下来的启用状态仍为 true，返回 400 并说明需要先关闭总额度，不静默改变开关状态。

升级前备份数据库。新数据库不承诺直接供旧二进制打开；回退使用升级前备份，避免旧程序误解开关和暂停规则。

## 8. 实现边界

模块职责：

- 新增渠道识别模块：固定渠道 ID、显示名称、实际模型分类；独立于上游连接。
- 策略与范围判断：区分持续记账、生效权限和生效额度，统一表达总量／渠道／模型查询范围。
- 现有引擎：复用准入、账本、补计、核对和原子保存机制。
- 数据迁移：补齐渠道与持续记账起始信息，保持旧账本和旧策略兼容。
- 页面：总额度开关、配置方式选择、渠道表格与共用额度弹窗。

只做支撑上述职责所需的代码拆分，避免继续把渠道字符串判断散落在前端和引擎里。不重写原生 ABI、价格同步或宿主鉴权。

本次不增加：自定义渠道、上游连接管理、渠道和模型同时生效、单模型覆盖渠道规则、逐渠道独立周期、用量明细页、多宿主共享额度、收费推理测试。

## 9. 验收标准

1. 旧数据升级后，总额度原有启停语义和模型权限保持一致；账本金额与 Token 不变。
2. 总额度开关关闭后，上限和用量保留，关闭期间持续记账；重新启用不重置周期。
3. 从未配置额度时，首次开启必须填写单位和上限；取消和保存失败不会产生生效状态。
4. 生效的总额度 0 拦截，关闭且保存为 0 时不因总额度拦截。
5. 按渠道时，GPT 多个模型共享用量；同一系列经不同上游调用仍归属同一渠道。
6. 渠道禁止涵盖其实际模型，别名不能改变实际归属；未识别模型进入其他渠道并受其规则约束。
7. 两种配置方式保存后严格二选一，另一套权限与额度完全不参与；切回时配置和历史用量均保留。
8. 渠道与总额度共同生效，但一次执行只记账一次；混合 Token／USD 独立判断。
9. 缺价、历史补计和待核对只影响生效范围；暂停规则不会拦截或要求补价。
10. 金额切换预览和确认准确，重叠范围只补计一次，失败不产生部分策略或费用更新。
11. 去重、重试实际消耗、跨零点、重启、人工核对及迟到修正保持一致。
12. 新字段缺失、非法模式、并发版本冲突和数据库迁移重入均有明确结果。
13. 浏览器验证两种表格、开关、首次启用、草稿保存、取消、补计确认和错误状态；桌面／窄屏布局、键盘操作及焦点恢复可用。
14. 官方宿主加载更新后的插件，使用本地模拟请求验证实际模型选择、渠道拒绝和账本结算；不以 DOM 测试代替宿主验收。

开发测试按用户既有约定使用临时测试源，验证后移除，留下准确的验证记录。任何工具策略拦截均如实记录，不将未完成的浏览器或宿主检查标记为通过。
